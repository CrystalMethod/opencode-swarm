# Epic Mode v2

## What changed

- **Breaking: Epic commits at LANDING, not at completion.** In a git epic every coder runs in an isolated worktree and its lane lands as a real merge commit (`git merge --no-ff --no-edit`) on the epic branch with the message `swarm(task <id>): <description>` and a final `Swarm-Plan: <planKey>` trailer (`planKey = sha256(planIdentityHash + '|' + planEpoch).slice(0, 16)`, unique per plan epoch). A task's work is therefore committed before `update_task_status(completed)`, and a rework coder — whose worktree is cut from HEAD — starts from the first attempt and lands without an overlap failure (before, an in-wave rework after a failed Stage B could never land). The landing is a non-interactive protocol commit (closed stdin, `--no-edit`, signing off, commit hooks skipped with `--no-verify` — they run when you commit the epic's squash at close). A landing is not attempted while the primary checkout has staged changes: the lane is preserved and `epic_next_wave` blocks `landing-index-dirty` (`EPIC_LANDING_INDEX_DIRTY`, naming the files to unstage). The former Epic "Rule 2" commit at task completion is removed: **`update_task_status` performs no git writes** under any configuration.
- **Required worktree isolation for epic coders.** A coder for a task of the open git epic is always worktree-isolated, whatever `parallelization_enabled`, `max_concurrent_tasks` or a session concurrency override say (an `auto` worktree policy acts as `required`). If isolation is unavailable the dispatch is refused with `EPIC_ISOLATION_DEGRADED` (remedy: retry, or `/swarm epic close --abandon`) — the coder never runs un-isolated in the main tree. Non-git epics keep running serially in the main tree.
- **Residue commits.** Main-tree files a non-coder writer (test_engineer, docs, …) wrote for an epic task are committed on the epic branch when its delegation returns (foreground or background), as `swarm(task <id>): <agent> residue` + the trailer — only that agent's attributed paths (the task's declared scope in the current wave, its write attribution, the agent's own session), literal pathspecs, `--only`, never `.swarm/`, serialized with worktree landings. A failed residue commit restores the index exactly, is a critical warning, and is retried when the wave closes. `blocked: dirty-baseline` now means uncommitted changes to **tracked** files when a new wave is about to start (the closing wave's residue is committed first); untracked files are only reported. Do not edit the working tree while a wave runs — edits inside a running task's scope can be committed as its residue.
- **Epic refs.** An epic keeps `refs/swarm/epics/<epicKey>/base` (start commit), `…/waves/<seq>` (HEAD at wave close) and `…/tasks/<id>` (the task's landing or residue commit, recorded at wave close), mirrored from the epic record (create-only `git update-ref`, idempotent). A completed dependency counts as predecessor evidence only when its task ref is an ancestor of HEAD (or it was completed before the epic started); a git failure blocks `git-failed`. `/swarm epic status --repair-refs` re-adopts a task commit a rebase or amend made unreachable (its `swarm(task <id>):` commit for this plan, else the newest commit touching its declared files; otherwise `needs-attention`). `/swarm epic close` (and `/swarm close` finalization) records every ref in the close report and deletes them, unless the new `turbo.epic.retain_refs: true`. The refs are not pushed or cloned by default (`--mirror` copies them).
- **Plan-scoped merge-failure epoch.** The shared `.swarm/worktree-merge-status.json` registry is keyed by bare task id and never cleaned. Epic ignores a failure recorded before its epoch (the wave's issue time for closing a wave, the epic's start for the auto-checkpoint skip); a failure with no timestamp stays relevant (fail closed). Completing an epic task whose merge-back failed skips the #2582 auto-checkpoint with a critical warning. `/swarm epic status` lists recorded merge failures as blocking, undated, or stale, with the remedy; `/swarm epic clear-merge-failure <taskId> [--confirm]` clears one that no longer reflects reality (without `--confirm` it only previews).

- **Breaking: an epic is now plan-scoped and opened explicitly.** `/swarm epic on` and `/swarm epic off` were removed (they now fall to the usage text). `/swarm epic start [--force]` opens one epic for the current plan; `/swarm epic close [--abandon]` closes it and writes a close report to `.swarm/epic/reports/` and `.swarm/epic-prior/reports/` (newest 50 kept, survives `/swarm close`). `/swarm epic status` shows the epic, detects an epic orphaned by a plan rename/replacement, repairs the `.swarm/epic/epic.json` sentinel, and retires Epic v1 per-session state once.
- **Start refusals.** `/swarm epic start` refuses, in order: `epic-disabled-by-config`, `no-plan` / `plan-ledger-unreadable`, `epic-already-open` (same plan — idempotent) / `epic-open-for-other-plan`, `turbo-active` (config `turbo_mode`, a session with Turbo on, or a running Lean run), `dirty-baseline` (git: uncommitted changes outside `.swarm/`), `in-flight-coders` (any coder dispatch, background delegation, unsettled settlement, or preserved/recovery lane in the project), and `not-epic-sized`.
- **Epic sizing.** A plan is epic-sized when it has at least `turbo.epic.sizing.min_tasks` (6) pending tasks, at least `min_scope_coverage` (0.8) of them carry a scope, and the Amdahl-adjusted speedup of a wave-planner dry run is at least `min_effective_speedup` (1.25, with `coder_fraction` 0.6). Otherwise the start is refused with the reasons and "run it in Balanced"; `--force` overrides and is recorded. Non-git projects run an epic serially (one task per wave), so they always need `--force`.
- **Epic branch (new default) and landing at close.** New `turbo.epic.commit_policy: "epic-branch" | "current-branch"` (default `epic-branch`). In a git project `/swarm epic start` checks out `swarm/epic/<epicKey>` and every Epic commit lands there; it refuses `detached-head` and `epic-branch-exists` (a leftover branch from an abandoned epic of the same plan — delete it with `git branch -D`), and rolls the start back (`branch-create-failed`) if the checkout fails. `/swarm epic close [--land squash|merge|none]` refuses a dirty tree, a missing original branch, and a detached HEAD whose commit would be orphaned before changing anything (an epic branch without changes reports `nothing-to-land`), then lands the branch onto the original branch: `squash` (default) leaves the epic's diff **staged and uncommitted** for you to review and commit, `merge` makes a `--no-ff` merge commit, `none` only switches back. The epic branch is never deleted by the plugin. A landing conflict is rolled back (`git reset --merge` for squash, `git merge --abort` for merge), the epic stays `closing`, and rerunning close resumes; landing is idempotent. `--abandon` and `/swarm close` never land — they switch back to the original branch when the tree is clean and keep (and name) the epic branch.
- **Branch drift is refused.** While an epic-branch epic is open, `epic_next_wave` blocks with `epic-branch-mismatch` (`EPIC_BRANCH_MISMATCH`, remedy `git checkout swarm/epic/<epicKey>`) when HEAD is not the epic branch, and neither a coder's landing nor a residue commit is committed onto another branch (critical warning).
- **Breaking: `epic_next_wave` replaces `epic_decide_phase`, `epic_plan_waves` and `epic_record_divergence`** (all three removed, with `/swarm epic decide` and `/swarm epic last`, the plan-wide `p` activation gate, and `.swarm/evidence/epic-promotions.jsonl`). The architect calls `epic_next_wave` (no arguments, idempotent) and does what its `status` says: `dispatch` (a wave of ready tasks with disjoint declared scopes, plus step-by-step instructions — one `Task` per task id in one message, per-task Stage A/B, then call again), `declare-scopes`, `in-progress`, `blocked` (`task-blocked`, `merge-failed`, `git-failed`, `dirty-baseline`, `predecessor-missing`, `plan-revised`, `task-reopened`, `epic-branch-mismatch` — each with its remedy), `phase-ready-for-review`, `epic-complete`, or `refused`. A wave closes once every task is completed, closed, or removed and none has a merge failure recorded since the wave was issued; phases run strictly in order — phase N+1 starts only after `phase_complete` of phase N (which now records the phase complete on the epic). Predecessors completed before the epic started need no task ref (their work was in HEAD at start); only the epic's current phase can be recorded complete by `phase_complete`. A closed or removed task's merge failure does not hold its wave, and the shared merge-status registry is trusted only while bound to this project. Global/protected-file tasks and tasks touching calibration-learned hot modules run alone; with `turbo.epic.cochange.enabled`, co-changing tasks go to different waves. The epic record keeps every wave (frozen declared scopes, base and close HEAD) and per-task outcomes (rework generation, Stage A/B failure lower bounds, merge-failure snapshot, reopen count, undeclared files), shown by `/swarm epic status` and the close report. Divergence is computed at wave close from coder-session attribution (git fallback: changes since the wave's base) and still feeds calibration. `epic_phase_review` refuses (`waves-open`) and `phase_complete` blocks (`EPIC_PHASE_WAVES_OPEN`) while a wave of the phase is open. The Epic banner is now short narration: "call `epic_next_wave` and do exactly what its status says"; per-task QA is never waived. `turbo.epic.mode.min_commits_for_signal` is no longer read; `activation_threshold` only bounds the calibration override shown by `/swarm epic calibration`.
- **One project probe drives every Epic behaviour.** The landing and isolation seams, residue commits, the auto-checkpoint guard, the `epic_phase_readiness` gate, the Epic banner, `epic_next_wave` / `epic_phase_review`, and per-task attribution retention all ask "is an epic open for the current plan?". The check is sentinel-first: a project with no open epic pays one `existsSync` — no database open, no config read, no write. The per-session Epic rows, their 24 h TTL and heartbeat, and the session-lifecycle hooks are gone; `/swarm reset-session` no longer touches Epic (an epic outlives a session); `/swarm close` closes an open epic as `abandoned-by-swarm-close` before archiving. While an epic is open the standard parallel-dispatch advisory is suppressed (the Epic banner and `epic_next_wave` own dispatch guidance), and each wave is capped at the epic's width.

- **Bundle size cap.** `dist/index.js` grows by about 127 KB with Epic v2's own code (upstream 9,895,994 B → 10,022,955 B); the packaging smoke cap `MAIN_BUNDLE_MAX_BYTES` is raised from 9.5 MiB to 10.5 MiB (#1583 precedent; #1582 identifier minification remains the structural fix).

## Why

Committing an epic task at completion deadlocked in-wave rework: the first attempt landed unstaged, the rework worktree (cut from HEAD) lacked it, and the rework's landing overlapped those uncommitted bytes forever; tests the test_engineer wrote stayed uncommitted and paused the next wave. Task ids also repeat across plans (every plan has a `1.1`), so history-grepped markers from an earlier plan could satisfy the current plan's dependencies; epic refs and plan-scoped messages bind every piece of evidence to this epic.

## Migration steps

- Architect prompts or automation that call `epic_decide_phase`, `epic_plan_waves` or `epic_record_divergence` must call `epic_next_wave` instead. `/swarm epic decide` / `/swarm epic last` are gone; use `/swarm epic status`.
- Replace `/swarm epic on` with `/swarm epic start` (once per plan) and `/swarm epic off` with `/swarm epic close` (or `/swarm epic close --abandon` with tasks still pending). Legacy Epic v1 per-session state is retired the first time `/swarm epic status` runs; nothing is opened automatically.

- Epic tasks no longer get a commit from `update_task_status`. Close an epic opened before this release (`/swarm epic close`, or `--abandon`) and start a new one; its coders then land as commits.
- To make a hand-made commit count for a task, give it the subject `swarm(task <id>): …` and a final `Swarm-Plan: <planKey>` line (the plan key is shown by `/swarm epic status`), then run `/swarm epic status --repair-refs`.
- Mirroring a repository with `--mirror` also copies `refs/swarm/*`; ordinary push/clone does not.

## Known caveats

- Epic keeps Turbo off where it can see it: `/swarm epic start` refuses on config `turbo_mode`, a Turbo session in the same process, or a running Lean run; while an epic is open, config no longer seeds Turbo into new sessions, restored sessions come back with Turbo off, and `/swarm turbo` refuses to enable it. Turbo enabled in a different OpenCode process on the same project is not detectable.

- A residue commit attributes a non-coder writer's files by declared scope and session write attribution; a manual edit to a tracked file no task declared still blocks the next wave (`dirty-baseline`) until you commit or discard it. Declare each task's test files in its scope.
- Landing merges and residue commits skip repository commit hooks (`--no-verify`) and signing; they run when you commit the epic's squash at close.
- A plain `git rebase` of the epic branch drops the landing merge commits unless `--rebase-merges`; after any rewrite run `/swarm epic status --repair-refs`.
- A lane recovered later via `/swarm lanes` lands through the recovery path's own committed merge with its default message; its task commit is recorded as the wave's close HEAD.
- Renaming or replacing the plan while an epic is open orphans the epic: Epic behaviour turns off for the new plan, `/swarm epic status` says why, and `/swarm epic close --abandon` closes it.
- With the default `epic-branch` policy, keep the epic branch checked out until the epic closes; switching branches mid-epic stops Epic planning, and landings / residue are not committed until you switch back. Set `turbo.epic.commit_policy: "current-branch"` to keep the previous behaviour (commits on the branch current at start, nothing landed at close).
- `--land squash` stages the epic's changes without committing them; the `swarm/epic/<epicKey>` branch stays until you delete it, and starting a new epic for the same plan is refused while it exists.

- Plan-ledger re-roots: a `save_plan` that renames the plan's title or swarm, `/swarm rollback`, or a truncated-ledger recovery mints a new plan root, which orphans the open epic (see above).

# Live-proof fix: PR-review structured receipts can settle again

The #2585 live proof (AC11) drove a frozen benign PR through the real OpenCode host and exposed a default-path defect present on main: the collect-time discovery validation in `collect_lane_results` built its expected-workflow-identity without the live instance/revision/base triple, so every child-submitted structured receipt was rejected with `missing live workflow instance/revision/base identity` — deterministic, prompt-insensitive, and unrepairable from the orchestrator. Every base dimension settled as a contract failure and the workflow could only end in a forced-INCOMPLETE `NO_COVERAGE` disclosure instead of a truthful review verdict.

`collect_lane_results` now derives the identity triple from the lane's durable delegation record (workflow-instance binding + generation) cross-checked against the dispatching parent's live gate state (merge base and instance), and supplies it to the collect-time validator. An exact child-bound receipt settles as it always should have; a stale record from an aborted-and-reactivated workflow still refuses (instance cross-check), and any missing leg keeps the validator's explicit missing-identity rejection instead of guessing. Pinned by `tests/unit/tools/dispatch-lanes-collect-identity-2585.test.ts`, whose composed leg reproduces the live failure shape (same receipt and gate: rejected without the identity, accepted with it).

## AC13 — the architect-parent repair lever

When a lane's child session dies before submitting (a liveness-terminal lane: `cancelled` / `stale` / `error` carrying the #2615 typed `workflowLaneFailureClass: 'liveness'`), the lane's DISPATCHING parent session may submit exactly one repair receipt for that dead lane through `submit_pr_review_result`. The lever is strictly record-state-gated — never time-based — so an alive-but-slow child never qualifies, and every other session (including a sibling architect from another swarm, the #2609 shape) keeps the frozen exact-child refusal. The receipt stays bound to the dead child and carries architect provenance.

Authentication widening (review-hardened): the receipt gains optional `submittedBy: 'workflow_parent'`, `submittedByParentSessionId`, and `laneTerminalStateAtSubmission` fields, and the atomic receipt publisher accepts a `parentRepair` marker that admits publication onto the liveness-terminal lane only while the authoritative under-lock recheck still observes the typed liveness class. The submit gate additionally requires the record's workflow instance to match the active gate state and its workflow generation to equal the live `state.revision` — a same-instance superseded-generation liveness record is refused with the typed `superseded workflow generation binding` reason instead of reaching the publisher and failing with the masked immutable-identity reason.

The repair lever may only record the truthful unresolved-terminal state: an envelope whose outcome is not `INCOMPLETE` is refused at the gate with `architect-parent repair may only record an unresolved-terminal (INCOMPLETE) outcome` — a CLEAN/FINDINGS attestation via the lever would claim coverage the dead child never produced. The workflow then completes as a disclosed INCOMPLETE (NO_COVERAGE with the lane's unresolved dimension), never a silent success. Pinned by `tests/unit/pr-review/architect-repair-lever-2585.test.ts` (terminal-shape repair legs, multi-swarm closed door, alive-but-slow refusal, instance-only and generation-only stale-binding refusals, and the INCOMPLETE-only outcome gate).

## What

Opted-in automation status persistence (`automation.mode` = `hybrid`/`auto`) can no longer prevent the plugin from returning its manifest. Previously the init-path write of `.swarm/automation-status.json` was an unguarded inline `mkdirSync`/`writeFileSync` inside `initializeOpenCodeSwarm`: a directory conflict (`.swarm` occupied by a regular file), an unwritable path, or a write conflict (`automation-status.json` existing as a directory) threw through `AutomationStatusArtifact.updateConfig`, rejected the plugin `server()` entry, and the host silently dropped the plugin — no agents, no tools, only a FATAL banner (issue #2669).

## Fix

- The artifact write is now registered on the wrapper-owned post-resolution task queue (`automationStatusArtifactPostInitTask`), so it runs only after the manifest is delivered; its latency no longer counts toward the init budget (AGENTS.md invariant 1, "Bounded is not free").
- The writer itself is contained: every mutator fails closed with exactly one bounded, categorized, debug-gated diagnostic (`status artifact write failed (non-fatal)` with `operation`, `category`, `code` — no paths or stacks). Categories: `dir_conflict`, `path_is_directory`, `permission`, `volume`, `missing_path`, `unknown` (documented fallback for un-mapped platform codes). The in-memory snapshot still advances.
- The preflight integration's handler-time `recordOutcome` carries its own bounded non-fatal catch (the scheduler wrapper does not cover event-handler-time calls).
- New operator docs: `docs/automation-status.md` — the artifact is optional, the failure-category table, and how to diagnose a missing status artifact without confusing it with a plugin load failure.

## Verification

- New regression tests: writer containment (`tests/unit/background/status-artifact-nonfatal-2669.test.ts`), full-boot init containment with deferred-task proof (`tests/unit/index-automation-status-init-2669.test.ts`), and a defect-class source-scan ratchet that fails if any `AutomationStatusArtifact` mutator is ever re-inlined on the awaited init path (`tests/unit/index-automation-status-init-scan-2669.test.ts`).
- New Node ESM/host harness `bun run repro:2669` (matrix: opt-in/default × normal/corrupt/read-only fixtures against the built bundle, plus a Bun bundle-load check): pre-fix the corrupt opt-in fixtures rejected `server()`; post-fix every fixture returns the mandatory manifest shape and the process exits with no leaked handle.
- Node-ESM import of the built bundle, bundle-portability, and plugin-shape suites re-run green; the v1 `{ id, server }` default export is unchanged.

# Task recovery status categories and receipt-linked repairs

- `/swarm diagnose`'s Coder Settlements check now classifies every task's recovery facts with the shared vocabulary — missing / stale / ambiguous / corrupt / live_wedge — each line carrying the task's owning transition id and workflow generation, a per-class suggested next command (never `/swarm recover` for the corrupt class, which recovery refuses), and explicit uncertainty for live foreign or in-process owners. Healthy tasks are reported as a count only. The wedged Stage A class and plan tasks with no receipt at all are now visible instead of silently absent (#2665).
- Deterministic repairs now emit receipts linked to their predecessors: settlement recovery's `recovered` event carries `previousTransitionId`, `previousState`, and `expectedGeneration`; the Stage A repair's `repaired` event carries `predecessorTransitionId` (the transition that wedged the task). `/swarm recover` also prints shell-correct invocation quick forms, and its corrupt-WAL wording points at the runbook instead of an unusable command.
- New operator runbook `docs/troubleshooting/recovery-runbook.md`: one shell-correct invocation per supported shell — host command path, PowerShell (single-quoted), Git Bash (doubled leading slash `//swarm …` because MSYS rewrites a single leading-slash argument; `MSYS_NO_PATHCONV=1` globally breaks `--dir /c/...`), and the shell-neutral CLI — plus the meaning of each status category and the boundary between deterministic repair and external side effects needing human reconciliation. No runtime shell detection was added; the guidance is static.

# PR-review dead-family trigger-eval settlement, dispatch default, and digest instruction (issue #2835)

## What

- **Dead-family trigger-eval settlement.** `write_pr_review_trigger_eval` now admits a `MATCHED` trigger row whose cited micro lane is liveness-terminal — settled by the presumed-stale sweep with `workflowLaneFailureClass: 'liveness'`, terminal status `stale` or `error`, and no retained artifact — as a disclosed dead family instead of failing the whole receipt. Previously, a single required family whose every lane died of host abandonment made the trigger-eval receipt structurally unwritable: every downstream gate (candidate-inventory widening, supersession write, reviewer/critic dispatch, terminal completion) keys on the persisted receipt, so `abort_pr_workflow` was the only compliant exit even with base coverage settled and disclosed. The admission is verified from the durable delegation record itself (micro mode, family ownership, exact `pr_head_sha`/`gitHead` identity, liveness class, no retained output) — never from caller text. The receipt records one `coverage_degradations` entry naming the dead batch/lane and its terminal status; the family is UNATTESTED, the review proceeds as a disclosed PARTIAL, and the PARTIAL verdict matrix already forbids APPROVE. Operator-cancelled lanes are deliberately excluded (`cancel_pending` is a controlled act — re-dispatch the family).
- **`max_concurrent` documented default honored.** The PR_REVIEW base-dispatch acknowledgment checks (tier L exact-six, tier M/S partition, staged canary and fanout) now compare the defaulted value (`max_concurrent ?? lanes.length`) instead of the raw argument, matching the schema's documented "defaults to lane count". An explicit non-matching value still fails; non-PR_REVIEW paths are unchanged.
- **Lane prompt carries the `revision_digest`.** The structured-settlement instruction in the controller-bound PR workflow contract now renders the exact 64-hex `revision_digest` the lane must pass to `submit_pr_review_result` (whose schema requires it). Previously the instruction named only `batchId`/`laneId`, so first-wave lanes following it literally submitted without the digest and burned a full lane on a deterministic contract failure.
- **Skill protocol (canonical `.opencode` copy; `.claude`/`.agents` are adapter shims).** `swarm-pr-review` documents the dead-family settlement (retry first: initial attempt plus up to 2 retries — the wording now says so explicitly), extends the Phase-6 reviewer join barrier with "or disclosed as a liveness-terminal dead family on the persisted trigger receipt", states that an operator-cancelled lane does not qualify, and notes abort is legitimate only after this settlement path is exhausted.

## Why

A traced tier-M review lost a completable PARTIAL result: 5/6 base receipts were settled truthfully, but two micro families died of host abandonment at ~30 minutes each with no retained artifacts, the trigger receipt could not be written, and the run aborted. Issues #2181 (degraded coverage instead of abort) and #2383 (truthful N-of-6 settlement) established the disclosed-settlement principle for base lanes; this extends it to the artifact-less liveness-dead micro family at the trigger-eval gate.

## Notes

- Receipt and delegation-record schemas are unchanged; the disclosure rides the existing `coverage_degradations` array that the candidate-inventory derivation already consumes for disclosed skips.
- Recorded residual (follow-up candidate, not in this change): the artifact-less admission binds identity on `prHeadSha`/`gitHead` (the durable workspace snapshot carries no revision digest), and the collection-time null-digest path still settles a lane as `error`/`contract` rather than remaining pending. Both are noted on issue #2835.
- Guardrails: seven committed regression tests pin the settlement (admission + downstream inventory skip), fail-closed provenance (forged batch, non-liveness terminal), the dispatch default (accepted and rejected cases), the digest instruction, and the dispatch-time digest hard-fail.

## What changed

- The `plan_cursor` configuration block (`enabled`, `max_tokens`,
  `lookahead_tasks`) is now actually honored. Previously it was accepted by the
  schema and documented, but no production code read it — every setting was
  silently ignored (dead advertised config, audit finding CONFIG-F-02).
- Both context-injection paths now share one resolver
  (`resolvePlanCursorControls`, src/hooks/extractors.ts):
  - Path A (default, non-scoring): `enabled: false` suppresses the
    `[SWARM PLAN CURSOR]` injection; `max_tokens` and `lookahead_tasks` now
    shape the emitted cursor.
  - Path B (opt-in `context_budget.scoring`): same gates and options — and the
    scoring path now emits the plan-cursor candidate at all. It previously
    produced none for any real workspace shape, because its plan.md read lived
    in a branch that only executes when the structured plan fails to load,
    while `loadPlan` migrates a markdown-only plan into a structured Plan. It
    also gains the same `DISCOVER`-mode suppression Path A already had.
- The context budget report's `planCursorTokens` now accounts for the cursor
  that is actually injected (routed through `extractPlanCursor` with the same
  controls; exactly 0 when the cursor is disabled) instead of a bespoke
  30-line/1000-char approximation that no code path ever injected.
- Docs corrected: disabling the cursor keeps the phase header and current-task
  context injections (the real pre-v6.13 behavior). The old claim that
  disabling "falls back to injecting the entire plan text" described behavior
  that never existed and is removed from README.md and docs/architecture.md.

## Why

Issue #2580 (Workstream F, PR 16 of 21): accepted user controls must reach both
the normal and the scoring plan-cursor extraction paths; canonical token
accounting must stay consistent. With an absent `plan_cursor` block the default
(non-scoring) path's cursor text is byte-identical to the previous release, so
no migration is needed. Two observable default-config deltas are intentional:
opt-in scoring sessions now receive the plan-cursor candidate they were always
documented to have (it was structurally absent), and the budget report's
`planCursorTokens`/`swarmTotalTokens` now count the actually-injected cursor
(~2.5x the old never-injected approximation on the regression fixture), so
budget percentages may shift slightly downward or upward toward the truth.
Out-of-range values are clamped to the schema bounds (500-4000 tokens, 0-5
lookahead tasks).
